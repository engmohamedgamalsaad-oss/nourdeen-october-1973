# دليل مراجعة ودمج التغييرات في GitHub — مشروع خالدون

هذا الدليل يشرح طريقة مراجعة طلب دمج (Pull Request) ودمجه بأمان. **إنشاء طلب دمج لا يعني أن التغييرات دخلت إلى الفرع الرئيسي، والدمج لا يضمن وحده نجاح النشر على الموقع.**

## من الموبايل أو الكمبيوتر

1. افتح طلب الدمج الذي تريد مراجعته من رابط المشروع على GitHub.
2. في تبويب **Conversation** اقرأ وصف الطلب وأي ملاحظات أو تحذيرات.
3. افتح **Files changed** وراجع الملفات التي ستتغير. لا توافق على تغييرات لا تفهم أثرها، خصوصًا ملفات الحكايات المنشورة أو إعدادات Supabase.
4. افتح **Checks** وتأكد أن الاختبارات انتهت بنجاح. إذا كانت معلّقة، انتظر؛ وإذا فشلت، لا تدمج قبل فهم السبب وإصلاحه.
5. إذا كان الطلب **Draft**، استخدم **Ready for review** فقط عندما تكون المراجعة جاهزة فعلًا.
6. بعد اكتمال المراجعة، اضغط **Merge pull request** ثم راجع رسالة التأكيد واضغط **Confirm merge**. قد تختلف الأزرار حسب صلاحيات الحساب وسياسات المستودع.
7. بعد الدمج، افتح **Actions** وتابع تشغيل النشر إن كان إعداد GitHub Pages يشغّله تلقائيًا.
8. افتح رابط الموقع المنشور واختبر الصفحة المتأثرة على الهاتف والكمبيوتر. افحص الروابط والصور واللغات والأزرار قبل اعتبار المهمة منتهية.

## الفرق بين الحالات

- **Open / Draft:** التغييرات في فرع منفصل؛ لم تُدمج بعد.
- **Merged:** دخلت التغييرات إلى الفرع المستهدف، مثل `main`.
- **Deployment successful:** انتهى النشر بنجاح؛ يلزم مع ذلك فتح الموقع للتحقق من النتيجة الفعلية.

## احتياطات مشروع خالدون

- لا تدمج طلبًا يتضمن اختبارًا فاشلًا أو لم يُختبر مساره الأساسي.
- لا تنشر حكاية قبل الموافقة الصريحة على محتواها.
- لا تشغّل SQL أو تغيّر Supabase لمجرد أن طلب الدمج يحتوي ملفات SQL.
- إذا ظهر خلل بعد الدمج، أوقف أي تغييرات إضافية، وثّق المشكلة، واستخدم طلب إصلاح أو تراجعًا واضحًا بدل حذف ملفات أو بيانات يدويًا.
- في طلب المسار اليدوي رقم **#158** تحديدًا، يجب اختبار الحفظ والاسترجاع، اللغات الأربع، الأسئلة، فتح المعاينة، وتنزيل ZIP، والتأكد من عدم حدوث نشر تلقائي قبل الدمج.
